# engram-gate Specification (v1.0)

- Version: 1.0
- Basis: the gate contract (C2) of the EngramMesh design, and a
  reference pilot implementation.
- Terminology policy: every normative sentence here is written in systems
  terminology. Neuroscience analogies are not part of this specification.
- Korean edition: `SPEC.ko.md` sits next to this document. This English
  edition is the normative original.

---

## 1. Purpose and Scope

engram-gate is a **deterministic coordination gate** that runs before work
begins. Before an agent starts a task, it queries a shared trace store and
learns, as an **exit code**, whether related prior work exists.

- This contract is **advisory**. Exit 0 never blocks work. It presents
  evidence; the caller decides (stigmergy: coordination via the shared
  store, no direct messaging).
- The contract path — ingestion (C1) and query (C2) — MUST be **fully
  deterministic**. Nothing on this path may consume tokens: no LLM calls,
  no embeddings.
- This specification is **store-agnostic**. It MUST work with any trace
  store that satisfies the adapter interface in §6.

## 2. Exit Code Semantics

| Code | Meaning | Caller obligation |
|---|---|---|
| `0` | Related prior work exists | Read the JSON evidence on stdout and plan to avoid duplication or conflict (SHOULD) |
| `1` | No related prior work | Work may begin |
| `2` | Error (timeout, backend failure, invalid input) | MUST NOT be read as "no prior work". A timeout is not a green light. The caller SHOULD retry or hold the work |

This separation is the contract's safety property: "cannot answer" must
never read as "no problem."

## 3. Query Syntax

```
gate query "<keywords>" [--days N] [--no-refresh] [--agent <id>]
```

- `<keywords>`: a space-separated list of keywords. Empty means exit 2
  (MUST).
- `--days N`: how far back to look, in days. Omit it and the store's
  default applies.
- `--no-refresh`: skip delta ingestion (don't advance the watermark).
  Use this when results must be reproducible, e.g. against a frozen corpus.
- `--agent <id>`: who is asking. Recorded in the ledger; it MUST NOT
  affect scoring.

Operation order (MUST):

1. Unless `--no-refresh` is given, absorb pending deltas first (advance
   the watermark).
2. Score every visible entry in the store: per keyword, case-insensitive
   substring match against title (2 points), body (2), topics (1), summed
   per keyword — the full definition is §4.
3. Return entries with score > 0, highest score first.
4. Hits present → exit 0. No hits → exit 1. Anything failing in
   between → exit 2.

## 4. Score Function (Deterministic)

### 4.1 Score definition

```
score(s) = Σ_k (2·titleHit(s,k) + 2·bodyHit(s,k) + 1·topicHit(s,k))
```

- `titleHit(s, k)`: 1 if query keyword k occurs as a substring of the
  entry title, else 0 — judged per keyword (MUST).
- `bodyHit(s, k)`: same, over the body (summary included).
- `topicHit(s, k)`: same, over the topic list.
- Scores sum per keyword. No artificial cap (MUST NOT) — capping and
  display truncation are different things (§4.3).

### 4.2 Normalization

- Matching is case-insensitive (MUST). Beyond lowercasing, no linguistic
  processing (MUST NOT). Morphological analysis is out of scope — the one
  exception is a fixed synonym table at the adapter layer (§4.4).
  Embedding- or LLM-based expansion is prohibited.

### 4.3 No score cap; display truncation is separate

- **Scores are never capped** (MUST NOT cap). Ranking is what the
  contract is for; a cap destroys ranking information.
- **Display truncation (`LIMIT N`) is a different thing.** Returning
  fewer hits is not capping scores, and it is permitted. The truncation
  count is a deployment policy value, outside this contract.
  When truncating, the ledger (§7) SHOULD keep the total hit count
  alongside the displayed count.

### 4.4 Deterministic synonym mapping at the adapter layer

- At the adapter layer (§6), keyword expansion through a **fixed synonym
  table** (query term ↔ heading term) is permitted (MAY). The table MUST
  be a version-pinned static asset, and the determinism rule below
  (§4.5) applies unchanged — anything generated by statistical learning,
  embeddings, or an LLM is prohibited (MUST NOT).

### 4.5 Determinism contract

- Same input, same output (MUST). The score function MUST NOT depend on
  wall-clock time, randomness, or external API calls.

> §4 is the **baseline contract (arm v1)** — an *arm* is a defined score
> or retrieval variant. Experimental arms, exemption scopes, and latency
> relaxations are defined in Appendix A. Exit code semantics (§2) hold
> for every arm, no exceptions (MUST).

## 5. Output Format

- Exit 0/1: JSON on stdout (MUST).

```json
{
  "exit_code": 0,
  "hits": [
    {"id": "sess_x", "score": 12, "title": "..."}
  ]
}
```

- `hits` MUST be highest-score-first. Each hit MUST carry at least `id`,
  `score`, and `title`. Provenance (e.g. which ledger row it came from)
  is recommended (SHOULD).
- Exit 2: `{"error": "<reason>"}` JSON on stderr is recommended (SHOULD).

## 6. Store Adapter (Plug-in)

The gate asks only this much of a store (MUST):

```
list_visible(since) -> [{id, title, body, topics, ts}]
```

- Visibility scoping and filtering belong to the adapter.
- The gate core never looks inside: graph DB, vector index, or flat
  files — the contract is the same either way.
- The reference implementation ships a JSONL adapter by default (SHOULD).

## 7. Query Ledger Schema

Every query MUST be appended to an immutable ledger — the audit trail,
for false conflict analysis and provenance reconstruction.

```json
{
  "query_id": "20261012T010203Z-agent1-0001",
  "agent": "<caller id>",
  "keywords": "<original keywords>",
  "exit_code": 0,
  "hit_count": 8,
  "score_vector": [12, 8, 5, 4, 4, 4, 2, 2],
  "ts": "<ISO-8601>"
}
```

- `query_id` has the form **`ts-agent-seq`**: a UTC timestamp
  (`YYYYMMDDTHHMMSSZ`), the agent id, and a zero-padded sequence number,
  joined with `-`.
- `score_vector` lists the returned hits' scores, highest first (MUST).
- Append-only (MUST). No edits, no deletes.
- Monitor two numbers: ledger growth rate, and the exit-2 ratio (how
  often the gate can't answer).

## 8. Operational Contract

- **Latency budget**: p95 ≤ 5s is the default (SHOULD). Past that, the
  query MUST escalate to exit 2 on timeout. An arm may carry a relaxed
  threshold instead — marked with a star, ceiling 2× the default
  (p95 ≤ 10s); the rule is in Appendix A.3.
  The reference implementation enforces this rather than declaring it:
  the query path runs under a per-query watchdog (`--timeout SECONDS`
  on the CLI, `timeout` on the MCP tool; default 5 s — the budget's
  ceiling). The threshold itself is a deployment policy value, outside
  this contract (cf. §4.3).
- **Exit 2 is not a green light** (§2). If a caller policy chooses
  fail-open anyway, that decision and its reasons SHOULD be recorded on
  the caller side.
- **No push**: the gate MUST NOT contact agents that didn't query it.
  Consumers pull.

## 9. Non-Goals (Out of Scope)

- LLM-based re-ranking and semantic search (a separate extension
  document).
- Distributed consensus and global locks — deliberately absent; locks
  would contradict the advisory semantics.
- The C3 consolidation pipeline and promotion policy (a separate
  specification).
- Authentication and access control — the deployment environment's
  job, handled at the adapter layer.

## Appendix A. Arm Rules (Single Definition Site)

> An arm is an experimental score or retrieval variant on top of the
> baseline contract (v1). Arms are defined in this appendix. Exit code
> semantics (§2) hold for every arm (MUST). Status **Frozen** means the
> definition is fixed and will not change.

### A.1 Arm table (summary)

| arm | Definition | Status |
|---|---|---|
| v1 | Baseline contract (§4 as-is) — default path, regression gate | Frozen |
| v2 | Lexical score + Hebbian edge weighting (bounded tie-breaker) | Frozen |
| v3 | Body grading (per-keyword match counts) + Hebbian edge weighting | Frozen |
| v4 | Body grading + recency boost (60 min / 24 h) | Frozen |
| v5 | v4 + file overlap, restricted to the caller's session (`--session`) | Frozen |
| v6 | Vector / reciprocal rank fusion (RRF) retrieval arm — 3-cell comparison (keyword control / vector only / RRF) | Implemented as an experiment tool; not in the CLI |
| v7 | Subgraph context view arm — depth-k neighbours of hit sessions | Implemented as an experiment tool; not in the CLI |

- Arm numbers never change. Ledger rows are interpreted by number,
  so renumbering would corrupt them (MUST NOT). New arms take the
  next number from v8 by adding a row here — no main-text revision
  needed. No reuse, no skipping (MUST). Retired arms stay on the table,
  marked retired, never deleted.
- v6/v7 provenance: "Implemented as an experiment tool" means standalone
  pilot scripts — `tools/t22_arm_v6.py` (v6, 3-cell) and
  `tools/t23_arm_v7.py` (v7, depth-2) in the companion pilot repository,
  the "reference pilot implementation" cited under Basis. They are
  deployment-bound (pilot store + embedding endpoint) and deliberately
  not vendored into this package; the table above remains the single
  definition site.

### A.2 Exemption scope

- Arms are exempt **only** from §4.5 (the determinism contract) — an
  arm may use non-deterministic signals like embedding similarity. Then
  it SHOULD record what reproduction needs: model version pinned, corpus
  snapshot hash, query set fixed.
- **§5's output schema and §8's latency contract are not exempt**
  (MUST). An experimental arm still MUST NOT break consumer parsers or
  the latency budget. The latency threshold itself may be replaced by a
  per-arm relaxation under A.3.

### A.3 Latency relaxation thresholds (starred-table rule)

- Default: §8, p95 ≤ 5s. An arm may carry a relaxed threshold marked
  with a star (\*), ceiling **2× the default (p95 ≤ 10s)**. Past the
  relaxed threshold, exit-2 escalation works exactly as usual (MUST).
- Currently starred: **v6**\* (precomputed embedding lookup + RRF),
  **v7**\* (depth-k graph traversal). v2–v5 use the default.

## Appendix B. Glossary (non-normative)

- **stigmergy**: coordination through traces left in a shared
  environment. Agents don't message each other; they read what others
  left behind and decide for themselves. Standard term in multi-agent
  systems literature (after Grassé, 1959).
- **watermark**: a stored position marking how far delta ingestion has
  advanced. "Advancing the watermark" means absorbing pending deltas.
  Standard concept in stream processing — first-class in Flink and
  Apache Beam; Kafka Streams uses a similar stream-time mechanism.
- **fail-open**: on error, proceeding as if nothing was wrong. Exit 2
  exists so the gate never fails open silently. Established term in
  system and security design: fail-open keeps operating on failure,
  fail-closed blocks. Distinct from fail-safe, which means minimizing
  harm.
- **Hebbian weighting**: strengthening associations between items that
  co-occur — "fire together, wire together" (Hebb, 1949). Here, a
  bounded tie-break signal for the v2 arm, not a learning system.
- **RRF (reciprocal rank fusion)**: combining ranked lists from
  different retrievers by reciprocal rank (Cormack, Clarke &
  Buettcher, SIGIR 2009). Used in the v6 experiment arm.
- **tie-breaker** (also written tie-break): a secondary signal used only
  when primary scores tie; it can't overturn a score difference
  ("bounded").
- **undetected conflict**: overlapping or contradictory work by two
  agents that neither agent knows about — the concurrent-systems
  analogue is a write-write conflict with no visible error. This is
  what the gate exists to surface. Distinct from a race condition
  (timing-dependent outcome) and a lost update (one write clobbering
  another): here the defining feature is non-detection.
- **false conflict**: a flagged conflict that turns out not to be one —
  the counterpart of an undetected conflict. Used in ledger analysis.
- **C1 / C2 / C3**: EngramMesh design identifiers used as cross-references
  here — C1 the ingestion path, C2 the gate query contract, C3 the
  consolidation pipeline. Defined in the EngramMesh design, not in this
  specification.
